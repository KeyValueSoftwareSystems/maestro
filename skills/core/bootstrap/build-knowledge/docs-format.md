# Living docs format

One format for the workspace docs, whichever tool writes them: Maestro's `build-knowledge`
and `retrospect`, or the template's `workspace-index` when Maestro is not installed.
When Maestro is installed it is the only writer; the template hands off to `/build-knowledge`.

The docs hold only what an agent cannot cheaply read from the code: business rules, invariants,
what a change sets off in other domains, and where the code misleads. Everything the code already
says (endpoints, events, jobs, tables, config, calls between repos) is generated by a tool, never
written by hand or by a model. A doc is written for a person first: plain sentences, one fact per
row, links instead of searches.

## Layout and who writes what

```
AGENTS.md                         workspace map + rules that apply everywhere
docs/
  architecture.md                 written · level 0, read first
  <domain>.md                     one file per domain, in parts:
                                    written · summary, references, functional, technical,
                                              outbound side effects, maintenance
                                    TEAM · invariants, change scenarios
                                    generated · inbound side effects, cross-repo connections, inventory
  architecture.mmd                generated · from architecture's flows table
  code-to-facts.md                generated · checker only, never loaded into a prompt
  impact/side-effects.yaml        TEAM · change scenarios, machine-readable
  provenance.yaml                 generated
  codebase-maps/<name>.md         written · one map per repo
  anything else                   the team's own documents (see the last section)
<repo>/<folder>/AGENTS.md|CLAUDE.md  generated facts block, only in repos that opt in
```

`<name>` is the repo's folder under `codebase/` (in a single-repo workspace, the repo's own
folder name); `<repo>` is that repository's checkout.

- **Written**: by the docs writer (a model, reviewed by a person).
- **TEAM**: invariants (`INV`) and change scenarios (`CS`) are written and owned by the project's
  people, never by a model. A writer leaves them exactly as they are and puts what it finds under
  `## Proposed rules and scenarios`; Maestro's engine restores any change a writer makes to them.
- **Generated** files and blocks come from Maestro's `living_docs.py check --write`; never edit
  them. Without Maestro they are not produced, and the written docs keep this format.

**How a reader finds things.** Open the architecture first, then a domain doc's Summary (scope at
a glance) and its `depends_on` line (the other domains a change here can reach). Then read one
part: functional, technical, side effects, maintenance, or one inventory part. Follow a link or an
ID to anything else; never scan the repo for it. With Maestro,
`living_docs.py show <domain> --part summary|functional|technical|side-effects|maintenance|inventory`
prints just that part (`product` and `engineering` are the older two views).

Before format 4 a domain doc's sections had no parts (format 3), and before format 3 each domain
had two docs (`functional/`, `technical/`). Maestro's `living_docs.py migrate` moves either into
this format, every word kept; the Summary and References are then left for the writer.

**Domains** are the bounded contexts the code is organised around (`auth`, `payment-links`).
Name them in kebab-case. A domain may span several repos. Do not name domains after repos unless
the repo really is one bounded context. Write what the code **does today**, not plans. Re-running
refreshes in place: update existing rows, add rows and files for new facts, keep human edits.

## Rules for every written doc

1. **Front-matter** between `---` lines, then the `#` title:

   ```yaml
   ---
   doc: domain                    # architecture | domain
   domain: auth                   # domain docs only; equals the file name
   id_prefix: AUTH                # 2–6 capitals, one per domain; architecture uses ARCH
   owner: "Unknown. (ask: tech lead, since 2026-11-10)"   # a person or team; never invented
   depends_on: [member-profile, notifications]            # domain only: see below
   repos: [backend, web, mobile]
   code_roots: [backend/src/auth]                         # domain only: <repo>/<path> the domain lives in
   verified_at: {}                # written by the tool after each refresh; never by hand
   reviewed: {by: null, date: null}   # a person fills this when they review the doc
   status: draft                  # draft | reviewed | stale; the tool resets it to draft on every rewrite
   ---
   ```

   Never invent an owner or reviewer. A writer leaves `status: draft`; a person sets `reviewed`
   (or `stale` when they know it is out of date).
   **`depends_on`** lists every other domain this one affects or relies on: the one line an agent
   reads before changing the domain to know which other docs to open. It always includes every
   domain an Outbound or Inbound side effect names (Maestro's checker adds any that are missing);
   add a domain this one only reads from as well.
2. **IDs.** These facts take an ID, each defined in one section of the domain doc:
   `<PREFIX>-BR-NNN` business rule, `<PREFIX>-CL-NNN` client behaviour, `<PREFIX>-INV-NNN`
   invariant (team; `ARCH-INV-NNN` in architecture), `<PREFIX>-SE-NNN` outbound side effect and
   `<PREFIX>-CS-NNN` change scenario (team). Always three digits. A new fact takes the next free
   number (`living_docs.py next <PREFIX>`); never reuse or renumber. A business rule that no
   longer holds keeps its row with Status `removed`; another retired fact keeps its row and starts
   its second cell with `Retired YYYY-MM-DD:` and why. Proposals, alerts, edge cases and findings
   take no ID. Code and tests cite the invariant they enforce (`// PL-INV-001: why`).
3. **Anchors** point at code as `repo · path · symbol` (a function, type, method as
   `Type.Method`, test, table, operationId or config key). Never line numbers. A path ending in
   `/` names a folder. Every anchor must resolve.
4. **Links, not searches.** A document the domain relies on is linked from References; another
   domain is linked as `[domain](domain.md)`; a fact elsewhere is cited by its ID. Every local link
   must open.
5. **Unknowns are owned**: `Unknown. (ask: <who>, since <YYYY-MM-DD>)`, or a row in Open
   questions. A bare `Unknown.` fails. Ask a named person, not a role, when one is known.
6. **Rows stand alone.** Each row and bullet starts with the thing it is about, never "It",
   "This" or "They", so one row can be handed to an agent on its own.
7. **Headings.** Only the `#` parts and `##` sections listed for the doc, in that order, each
   section under its part. A required section is always present, with `None.` when there is
   nothing to say; an optional one is left out when empty. Tables use exactly the listed columns.
8. **One place per fact.** When the same fact is written twice, one copy goes stale and nobody
   can tell which is right. So:
   - a rule's wording lives in Business rules; every other section cites its ID;
   - an HTTP status lives only in Error codes (a rule names the error code);
   - a config default lives only in the generated Inventory § Config (a rule names the key);
   - an effect on another domain lives only in its Outbound row (a rule or flow writes
     "see AUTH-SE-001"); the target's Inbound table is generated from it;
   - endpoints, events, jobs and tables live only in the generated blocks;
   - shared terms live in architecture, domain terms in the domain's glossary.
   No build or test commands (those live in `maestro.config.yaml` and each repo's instructions).
9. **Budgets**, in tokens (about 4 characters each): architecture 3,000, domain 5,000 not counting
   its generated blocks. Over budget, cut what an agent can find in code, or split the domain.

## `docs/architecture.md`

Note: `> Start here, then open one domain doc. A diagram for people is in architecture.mmd.`
Title `# Architecture`. Sections (R = required):

1. `## System context and repos` (R): two sentences on the product and who uses it, then a table
   `| Repo or provider | Kind | Purpose | Owns data | Runs on |`, one row per repo and external
   provider. Runs on names where it is deployed and the anchor of its infrastructure definition
   when one exists.
2. `## Domain map` (R): `| Domain | Purpose | Repos | Owner | Doc |`, one row per domain, the Doc
   cell linking `[<domain>](<domain>.md)`. Every domain doc has a row; every link exists.
3. `## Cross-repo flows and contracts` (R):
   `| From | To | Operation / event | Protocol | Sync | Auth | Contract |`, one row per connection,
   the contract as an anchor or `<provider> API (external)`. The diagram is generated from it.
4. `## Platform-wide invariants` (R, TEAM): `| ID | Invariant | Where (repo · path · symbol) | Consistency |`
   with `ARCH-INV-NNN` rows: rules every repo keeps (money type, who may call a provider), or `None.`
5. `## Proposed rules and scenarios`: `| Kind | Proposal | Where (repo · path · symbol) | Evidence |`,
   written by the model: kind `invariant` or `change scenario`, no ID. The team accepts a row by
   moving it, with the next free ID, into its section.
6. `## Conventions and boundaries`: bullets for personal data and residency, the error envelope,
   trust boundaries, and where risk tiers and product docs live.
7. `## Glossary and aliases`: `| Term | Meaning | Code names and aliases | Not to be confused with |`,
   only terms shared by several domains.

## `docs/<domain>.md`

Title `# <domain>`, then a Summary and References, then five parts. R = required; TEAM = written
by people only; the rest is optional and left out when empty.

```markdown
# auth

## Summary                                                        (R)
3–5 lines: what this domain owns, who uses it and on which portals or screens, its main methods
or flows, and what it does NOT own (and which domain does).

## References                                                     (R)
| Document | Covers |
| [Sign-in spec](product/sign-in.md) | The OTP and password journeys, agreed with product |

# Part A: Functional

## Purpose and actors                                             (R)
Who uses this domain, on which screen or portal, and for what.

## Glossary
| Term | Meaning | Code names | Not to be confused with |

## Business rules                                                 (R)
| ID | Rule | Edge | Status | Source |

## User flows
1. Sign in with OTP: Login screen → POST /auth/otp → code sent (AUTH-BR-002) → …

## States and transitions
| Entity | From | To | Trigger | Actor | Rule |

# Part B: Technical

## Architecture
- Guards and middleware order, token or session model, transports, rate limiting, caching,
  background work.

## Client behaviour
| ID | Client | Behaviour | Source |

## Invariants                                                     (R, TEAM)
| ID | Invariant | Enforced by | Test evidence |

## Failure, concurrency and idempotency
- Races, partial failures, retries, what is left behind; each cites the rule it protects.

## Error codes
| Code | HTTP | Raised by | Web handling | Mobile handling |

## Security notes
- Known risks, accepted trade-offs, sensitive data handling.

# Part C: Side effects

## Outbound                                                       (R)
| ID | Trigger rule | Target domain | Effect | Target rule | Same transaction | On failure |

## Inbound                                                        (R, generated)
<!-- generated:inbound begin; from the other domains' Outbound tables by living_docs.py; do not edit -->
<!-- generated:inbound end -->

## Change scenarios                                               (R, TEAM)
| ID | If you change | Also change | Where |

# Part D: Maintenance

## Gotchas
- Traps that are not obvious from the code.

## Open questions                                                 (R)
| Question | Ask | Since |

## Proposed rules and scenarios
| Kind | Proposal | Where | Evidence |

# Part E: Generated from code

## Cross-repo connections                                         (R, generated)
<!-- generated:connections begin; from code by living_docs.py; do not edit -->
<!-- generated:connections end -->

## Inventory                                                      (R, generated)
<!-- generated:inventory begin; from code by living_docs.py; do not edit -->
<!-- generated:inventory end -->
```

What goes in each section:

- **Summary**: 3–5 lines, no table. A reader or agent sees the scope before the details. The
  checker warns outside 3–5 lines and fails when it is empty.
- **References**: every document the domain relies on, linked: the team's own documents about
  it (a spec, a PRD, a wiki export under `docs/`), its contracts, its codebase map. Covers says
  what the reader finds there. A local link must open; a web link is kept as given.
- **Purpose and actors**: what the domain does, who acts and from which screen or surface. At
  most five sentences.
- **Glossary**: domain terms only; Code names lists the names in code, logs and the apps.
- **Business rules**: one rule per row. Edge is the exception or surprising case, or `None.`.
  Status is `active`, `temporary` (with when it ends in the Edge) or `removed`. Source is where it
  comes from or where the code enforces it: a reference, PRD, incident, ticket, owned unknown,
  or one or more `repo · path · symbol` anchors. Name error codes, not HTTP statuses; name config
  keys, not their values; write "see AUTH-SE-001" for an effect on another domain.
- **User flows**: one numbered list per journey: screen → endpoint → result, citing the rules
  and side effects each step sets off. When a flow hands over to another domain, link that
  domain's doc, so a reader follows the flow without searching.
- **States and transitions**: one row per transition of each main entity; Rule cites the BR.
- **Architecture**: short bullets; anchors, not prose about the framework.
- **Client behaviour**: what each client (web, mobile, a partner) does on its own that a reader
  of the server cannot see: caching, retries, offline, token storage. Client is the client's name.
- **Invariants** (TEAM): what must always hold, the anchor that enforces it, and the test that
  proves it. A row with no test evidence is a proposal, not an invariant.
- **Failure, concurrency and idempotency**: bullets, each citing the rule it protects.
- **Error codes**: Code, HTTP status, the anchor that raises it, then one `<client> handling`
  column per client. `—` = that client never calls it; `?` = unknown (and add it to Open
  questions).
- **Security notes**: bullets.
- **Outbound**: the only place a cross-domain effect is described. Trigger rule is this domain's
  rule that sets it off; Target domain is a link `[notifications](notifications.md)`; Effect
  names the exact event, endpoint or table; Target rule is the target domain's rule it relies on,
  or `None.`; Same transaction is `yes` or `no`; On failure says what is left behind and who
  retries.
- **Inbound** (generated): every other domain's Outbound row that targets this domain. Edit the
  source domain's row, never this block.
- **Change scenarios** (TEAM): If you change names the thing and its anchor; Also change names
  what must change with it (citing IDs and other domains); Where names the anchors to change and
  the tests that verify it, and the scenario's source. Each may also be an entry in
  `docs/impact/side-effects.yaml` with the same ID (see below).
- **Gotchas**: code not to copy (with its anchor and what to use instead), extension points,
  alerts with where to start looking, known gaps and tech debt.
- **Open questions**: one row per question; Ask is a named person, Since a date.
- **Proposed rules and scenarios**: written by the model: Kind `business rule`, `invariant` or
  `change scenario`, the anchor, the evidence, no ID. The team promotes a row, with the next free
  ID, into Business rules, Invariants or Change scenarios once confirmed.
- **Cross-repo connections** and **Inventory** (generated): write the heading and the empty
  markers; the tool fills them.

## `docs/impact/side-effects.yaml` (TEAM)

Optional: the change scenarios, machine-readable, so feature-impact can follow them into every
repository they reach and the engine can check every name still exists. Maestro's YAML subset (no
anchors, no folded text); `living_docs.py scaffold` writes a starter.

```yaml
version: 1
scenarios:
  - id: PL-CS-001                   # the row's ID in the domain doc
    domain: payment-links
    summary: Disabling a payment link
    rules: [PL-INV-004]             # invariants at risk
    repo: cofee-backend             # default repository for the names below
    when_changing: ["internal/links/disable.go", "Service.Disable"]
    also_impacts:
      domains: [reminders]
      tables: [payment_links]
      queues: [link.disabled]
      endpoints: ["POST /v1/links/{id}/disable"]
      files: ["cofee-payer-app:lib/pay/link_expired_screen.dart"]   # "repo:path" for another repo
      symbols: []
    verify: ["TestDisablePublishesEvent"]
```

## Generated files

Never edit these; `living_docs.py check --write` rewrites them from code and contracts:

- Each domain doc's `Inventory` block: `### APIs` (operation, owner repo, handler, called by,
  contract), `### Events` (producers, consumers), `### Jobs`, `### Data` (tables), `### Config`
  (keys, defaults; secrets never shown). Scoped to the domain's `code_roots`, plus anything its
  written sections name. Read one part at a time.
- Each domain doc's `Cross-repo connections` block: each app call, the repo and handler it reaches.
- `architecture.mmd`: for people; agents read the flows table.
- `code-to-facts.md`: which IDs cite each anchor. For the checker only.
- **Facts blocks**, in repos listed under `docs.facts_blocks` in `maestro.config.yaml`: each
  folder's existing `AGENTS.md` or `CLAUDE.md` gets the rows anchored in that folder, so an agent
  editing there sees them.

Extraction reads OpenAPI, AsyncAPI, SQL migrations, `.env.example` and Kubernetes CronJobs in any
stack, plus common route, client, event, job and config patterns in Go, Python, JS/TS, Dart and
Java/Kotlin. A project adds its own under `docs.extract` (see `docs/project-config.md`).

## The checker

`python3 .maestro/engine/living_docs.py check --root . [--write]` fails on: malformed, duplicate
or wrongly placed IDs (R1); an ID cited in docs, run artifacts or code that is never defined (R2);
an anchor, or a name in `side-effects.yaml`, that does not resolve (R3); generated output that is
stale or hand-edited, including a `depends_on` that misses a related domain (R4); an app call no
repo serves (R6); front-matter, parts, headings, table columns, an empty summary, a reference
that does not open, a rule status, an invariant without test evidence, an open question without
a person or date, a side effect naming an unknown domain or another domain's rule, unowned
unknowns, rows that do not stand alone, a Domain map that does not match the files, or an older
layout (R7); and, in a writer's check (`--locked-from`), any change to the team's content, which
the engine restores (R9). It warns when anchored code changed since `verified_at` or a doc is
still draft (R5), when an invariant is cited in no code or test (R2), when a fact is written
twice (an HTTP status outside Error codes, a config default outside the inventory) or a summary
runs past five lines (R7), and when a doc is over budget (R8). In a writer's check, a problem inside the team's content is a warning for the team.
Every message says how to fix it. `living_docs.py rules` checks only the team's content against
the code (a feature's worktree with `--repo/--worktree`) and never blocks.

## `docs/codebase-maps/<name>.md`

The standing per-repo description a designer reads before changing that repo. One per repo.

- First line `# <name>: Codebase map`.
- `##` sections covering: entry points and key modules; how the repo is built, tested and
  run; the primary end-to-end flows and **every distinct execution mode** each runs in
  (single-turn or multi-turn, sync or async, batch or streaming, first request or idempotent
  retry, single- or multi-tenant…), what selects each mode and where it lives, as
  `path · symbol` anchors; the data model, APIs exposed and consumed, the auth or guard pattern,
  the error envelope, and the conventions a change must respect.
- Read the repo's own `AGENTS.md` / `CLAUDE.md` / `.cursor/rules` first.
- **Never write or edit the marker line** `<!-- maestro-codebase-map commit=… updated=… -->`.
  A tool stamps it after you write: `codebase_scan.py record` in Maestro, `./scripts/index
  stamp <name>` in the template.

## `docs/provenance.yaml`

Shared by Maestro and the template. Written by `workspace_sync.py record-knowledge` when
Maestro is installed, otherwise by the `workspace-index` skill. Never edit it by hand
otherwise.

```yaml
# Auto-generated index provenance (Maestro + workspace-index). Do not edit manually.
schema_version: 1
indexed_at: "2026-10-08T13:00:00Z"
docs_sha256: "<sha256 of all docs/**/*.md>"   # filled by Maestro record-knowledge
evidence: docs/architecture.md
evidence_sha256: "<sha256 of evidence file>"
repos:
  - name: backend
    path: codebase/backend
    branch: main
    commit: abc1234def5678...
    indexed_at: "2026-10-08T13:00:00Z"
```

## Other folders under `docs/`

Every other file under `docs/` is the team's own: a document people put there (a product spec,
a domain write-up, `docs/product/feature-catalog.md`, a PDF), plus anything `docs.sources` in
maestro.config.yaml lists outside `docs/`. These **source docs** outrank the living docs: a living
doc follows them, cites them as the source of a rule, and never contradicts one; where the code
disagrees, the difference goes to Open questions and to a person. Link each one from the
References of the domains it describes. A writer may
append to a source doc but never changes, removes, renames or deletes what it holds: the engine
(`source_docs.py`) puts the original back and keeps the writer's version as a proposal for a
person. A writer creates no other file under `docs/`. `docs/architecture.md` is Maestro's path:
a team document there must move (for example to `docs/product/architecture.md`) before the first
build.
