# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Guidance for working in this repo (`maestro` — the KeyValue AI-SDLC pack).

## What this repo is

A **deterministic workflow orchestrator for agentic coding harnesses** (Claude Code,
Cursor, Codex), shipped with an **example** AI-SDLC pack. The engine is the product; the SDLC
skills + workflows are a worked example meant to be forked or replaced. The load-bearing
separation: **the workflow owns *what/where/when*** (instruction, inputs, artifact path,
output fields, ordering) and **a skill owns only *how*** — so any agent step's skill can
be swapped (ours, the user's, or a third party's like Obra/Superpowers) without touching
the graph, and the engine injects the paths/inputs/contract into each subagent prompt at
runtime. It ships:

- **AI skills** (`skills/**/SKILL.md`) — the example pack, one per SDLC step (plan, design,
  implement, review, QA…) plus **`skills/maestro`**, the lead agent. Markdown prompts with
  YAML frontmatter (`name`, `description`, `tags`, `allowed-tools`). Devs invoke them as
  slash commands (`/prd-writing`, `/repo-implement`, …) or Maestro invokes them via subagents.
  Skills are portable: they must NOT hardcode artifact paths or their position in a
  pipeline — that lives in the workflow node. Two kinds live here beyond the SDLC steps:
  **bootstrap skills** (`detect-stack`, `maestro-init`, `maestro-sync`, `build-knowledge`, `retrospect`) and
  **per-stack reference skills** (`golang-patterns`, `react-testing`, `springboot-security`,
  `go-review`, …) — the "how" style guides and review checklists. See the stack-tag note below.
  **Source layout** — the `skills/` tree is organized into category folders (`skills/maestro`
  the lead agent; `skills/maestro-discuss` its side-chat partner for one interview question; `skills/core/sdlc/*` the SDLC steps; `skills/core/bootstrap/*`; `skills/core/reference/*`
  core reference skills such as `architecture-patterns`; and
  `skills/stacks/<stack>/*` grouped by `stack:` tag) so new skills have an obvious home.
  A skill's IDENTITY is its frontmatter `name` (unique across the tree), never its path —
  workflows pin by name, harness discovery and stack filtering key off `name`/`tags:`. The
  folder is organization only; **`install.sh` flattens the tree on install** — the installed
  `.claude/skills/<name>/`, `.cursor/skills/<name>/`, or `.agents/skills/<name>/` stays one
  dir per skill.
- **Stack tags & per-stack packs.** A skill tagged `stack:<x>` (e.g. `stack:go`,
  `stack:react`, `stack:django`) is a per-stack pack; anything WITHOUT a `stack:` tag is
  **core** and always installs. `install.sh --stack go,react` installs core + only those stacks;
  `/maestro-init` runs `detect-stack` to pick the filter from the repo automatically. A stack is
  knowledge, never a role: there are no per-stack agents — the one `reviewer` role gets a
  stack's `<x>-review` checklist as a skill, like every other stack skill. Frameworks carry their
  own tag (`django`, `fastapi`, `pytorch`), so a plain-Python repo is not handed Django's
  conventions; a Django repo lists both (`stack: python, django`). The per-stack skills are
  generated by `scripts/import_ecc.py` (reference skills: frontmatter normalised only; review
  checklists: an ECC reviewer agent's checklist without its persona and verdict); they
  are NOT pinned in any workflow node (the engine names the matching ones to each repository's
  implement/review/fix steps via `stack_skills.py`), so they are exempt from the SDLC-step contract (no
  artifact path, no Output-contract requirement).
- **The engine** (`engine/`) — stdlib-only Python. `maestroctl.py` is the CLI the lead
  agent shells out to: `validate · preflight · init · next · complete · complete-batch · gate-record · fail · reset
  · reclaim · rebase · migrate · status · todo · brief · profile · graph · note`. The resolver serves exactly ONE next action as JSON; the
  LLM never interprets the graph and never edits state. No dependencies, ever.
- **Workflows** (`workflows/*.yaml`) — the example pack (`sdlc-main`, `design`, `impl`,
  `qa`) in the custom spec. Large flows are split into small stage children so no graph is
  overwhelming in the builder (target: ≤ ~12 nodes each): `sdlc-main` composes `design` →
  `delivery` → `archive`; `design` composes `design-intake` / `design-prd`, then a `parallel`
  node running `design-solution` (impact, sizing, then `design-hld` with its architecture review /
  `scaffold` (greenfield only: create the repositories the HLD lists) / `design-contract` (only
  when the HLD lists cross-repo interfaces) / `design-lld` (every repo's LLD in one run)) beside
  `design-tests` (the functional test cases, from the approved PRD alone; QA takes exact values
  from the design when it runs them). `todo.py` lists a parallel of single-stage branches as
  those stages side by side. A gate decision
  that leaves its stage ends the child and is reported in its `outputs:`; the parent routes on it
  (gate-driven, so not visit-capped). Spec (`docs/workflow-spec.md`, machine contract
  `engine/schemas/workflow.schema.json`).
- **Agents** (`agents/*.md`) — the roles: `product`, `architect` (`planner` is its older name,
  kept for existing workflows), `implementer` (developer), `reviewer`, `qa`, `analyst`, plus
  `general`/`discussant`. Claude Code subagent definitions (tools + role prompt) installed into
  `.claude/agents/`. Every node names its role (`agent:`, or `defaults.agent`), and the engine opens
  each prompt with a `Role:` line from that definition, so the role holds for `execution: lead`
  jobs and on hosts without subagent types. Codex uses its native subagents, driven by the exact
  prompt and named skill served by the engine; Cursor uses inline mode.
- **The builder UI** (`ui/builder.html`) — single-file visual workflow editor, plus a
  read-only **Runs** view that reads `.maestro/runs/<slug>/state.yaml` and colours each run's
  graph by step status (done/running/failed/pending). Works offline from `file://` (browser
  File System API) OR folder-aware behind `engine/ui_server.py` when served by `maestro ui`
  (probes `/api/health`; then loads runs/workflows over HTTP — see the branch points guarded
  by `window.MAESTRO_SERVER`). `ui/embed.py` refreshes its embedded schema + lint-rule blocks.
- **`bin/maestro`** — a repo-local dev wrapper `install.sh` drops at the consumer repo root
  as `./maestro`. Subcommands: `maestro ui` (serve the builder via
  `engine/ui_server.py`), `maestro install` (proxy to `install.sh`), `maestro init` and
  `maestro sync` (`project_config.py init` / `sync`: config entries only). It is dev tooling
  only — it NEVER drives a run or writes run state; the Maestro skill + engine stay the
  sole execution path and only state writer.
- **`install.sh`** — the installer. There is deliberately NO **execution** CLI and NO config
  file: workflows only ever run through the Maestro skill + engine (the `maestro` bin above
  is viewer/installer tooling, not an executor). Artifact paths, inputs and the output
  contract are declared on the **workflow node** and injected into the subagent prompt by
  the engine — skills do NOT hardcode paths (that keeps them swappable). Accepts an optional
  `--stack go,react` filter: it copies the core skills and roles plus only the skills whose
  frontmatter `tags:` carry a matching `stack:<x>` token (parses the `tags:` line directly —
  no YAML dep). No flag / `--stack all` = everything. Skills/agents are the only filtered
  trees; commands and the runtime files always copy whole. **Install layout:** everything
  Maestro ships nests under one `.maestro/` parent in the consumer repo —
  `.maestro/{engine,ui}` (regenerated), `.maestro/{workflows,docs}` (committed), plus the
  engine-created `.maestro/memory/` and `.maestro/runs/<slug>/`. Only the `maestro` wrapper
  and `install.sh` sit at the repo root. Workflow files reference sibling workflows and
  engine scripts by the installed path (`.maestro/workflows/…`, `.maestro/engine/…`), so
  **this pack repo — whose source lives at `engine/`, `workflows/`, `ui/`, `docs/` at root —
  mirrors the installed layout via committed symlinks (`.maestro/engine → ../engine`, etc.)**
  so `validate .maestro/workflows/…` and dogfood runs resolve here too. The e2e test builds
  the same layout in a tmp dir.

There is **no headless runner and no API-key dependency** — workflows execute inside
the user's interactive session (Claude Code, Cursor, Codex). Conductor is gone.

## The engine — module map & the action loop

`maestroctl.py` is a thin CLI; the logic lives in modules it imports. Where things are
(so you don't grep blind):

- **`resolver.py`** (by far the largest — the centerpiece) — computes the ONE next action,
  and owns nearly all state mutation: frontier/`cursors`, resume rules, `when` evaluation,
  visit counting + cap enforcement, **back-edge cascade reset** (`_cascade_reset` /
  `_ancestors` — deliberate *under*-reset; read the docstring before touching it), parallel
  branch joins, subworkflow entry, placeholder substitution (`resolve_text/ref/value`,
  `missing_ok=True` for prompt / route-condition / step-input rendering so an unset step
  ref renders empty rather than aborting — but `model:`/`max_visits:` and typed init inputs
  resolve strictly), and
  **`render_agent_prompt`** (assembles the role line + instruction + inputs + skill pin +
  artifact list + a failed check's report + the last-line-JSON output contract into the agent
  prompt). It also owns lead-executed
  agents (`execution: lead`) and durable interviews (`record_interview`), including validated
  dynamic question queues and cumulative decision artifacts.
  `complete_step`, `record_gate`, `init` live here too.
- **`state.py`** — the ledger: load/save with `fcntl` lock + atomic tmp/rename, `step_entry`,
  step wall-clock timing, `sha256_file`, `new_state`. The ONLY writer of
  `.maestro/runs/<slug>/state.yaml`. The lock and the ledgers an `init --force` replaced live
  under the run's `.engine/` (`state.lock`, `ledgers/`), so the ledger is the only file at the
  top of a run folder.
- **`run_layout.py`** — where a run keeps its files, one folder per kind: `requirement/` (the
  request, `prd.md`), `design/` (`hld.md`, `openapi.yaml`, `lld/<repo>.md`, `test-cases.md`,
  impact), `decisions/` (the decision log and each stage's interview record), `reviews/`
  (`<name>.md` + `<name>.findings.json` + the author's `<name>.resolutions.json`), `build/`
  (`manifest.json`, `<repo>/tasks.json` + `verify.json`), `qa/`, `release/` (`review-pack.md`,
  `ac-trace.md`, `delivery.json`) and `.engine/` (queues, review baselines, sync plans,
  snapshots, logs: nothing written for reading). Workflows name these paths on their nodes; the
  helpers with a default take it from here, and `test_run_layout.py` holds the shipped workflows
  to it. `migrate` (run by `init` and `rebase` on a `run_format` 3 ledger, or `maestroctl
  migrate`) moves a flat-layout run in: files move and are never rewritten (approved hashes
  hold), the ledger and the engine's JSON records get their paths updated, `legacy_paths`
  tells `install_workflows.py` which run paths an edited workflow must rename.
- **`todo.py`** — the run's todo list, read-only: stages (subworkflow/parallel nodes) in order,
  the running stage expanded, optional stages only once entered, plus what the run is doing or
  waiting on the human for. `maestroctl todo` prints it; `init` and any `next` whose picture
  changed (digest in `run.todo_digest`) carry it as `todo`, which the lead mirrors verbatim into
  the harness's task list. Engine-built so every surface shows the same thing.
- **`validate.py`** — schema check + graph lint (start/route-target existence, reachability,
  default-route-on-branches, placeholder resolvability, subworkflow depth, cycle lint).
- **`condctl.py`** — the ~4-form route-condition grammar (`==`, `!=`, `in […]`, truthy);
  parses BEFORE substitution so values can't inject operators. `norm()` canonicalises
  bools/numbers; guards use `== true`/`== false`, never `!= true` (prose would slip through).
- **`wf.py`** — the zero-dep YAML-subset loader/emitter (see its own section below).
- **`oq_serve.py` / `oq_record.py`** — the open-questions `script`-node helpers (the
  stdout-JSON-becomes-routable-outputs pattern); `validate_tasks.py` /
  `validate_open_questions.py` — standalone artifact-format validators.
- **`validate_prd.py` / `validate_prd_questions.py` / `validate_hld.py` / `validate_lld.py`** —
  deterministic PRD, HLD, and repository LLD structure, acceptance-ID, readability, question-queue,
  and deferred-ledger checks. They never make product or architecture decisions.
- **`lld_set.py`** — the feature's repository LLDs, one file per selected repo
  (`design/lld/<repo>.md`), written and approved in one run: scope (`.engine/lld-scope.json`), validate the whole
  set, record a hash-bound approval (HLD, contract and each LLD), and `verify` at the start of
  delivery so a design that changed after approval goes back through design instead of being
  built stale.
- **`implementation_pool.py`** — the implementation queue: the golden workflow implements every
  designed repo afresh on each delivery pass (`init --choice all --fresh`); `--choice pick` still
  supports batches with deferred repos for team workflows. Builds the QA/release manifest only
  from exact verified worktree commits, with each repo's verify receipt and status attached, and
  whether that exact commit was code-reviewed (`.engine/reviews/code-<repo>.reviewed.json`, written by
  `findings.py verdict --commit --reviewed`); a commit accepted at the escalation gate before review shows
  `not-reviewed`, and autopilot will not release it.
  `bugfix-init`/`bugfix-claim` queue the repos a QA product bug names (`qa-bugfix.yaml` fixes each
  in its worktree) and `record --from-worktree` records the fixed HEAD.
- **`worktrees.py`** — the feature's implementation worktrees, made by the engine before any agent
  writes code: `prepare` runs `worktree.create` from maestro.config.yaml once per feature (e.g. the
  workspace template's sandbox command) and finds each repo at `worktree.path`, or adds its own at
  `.maestro/worktrees/<slug>/<repo>`; it uses only worktrees this run created (record:
  `.engine/worktrees.json`), new ones must be clean and at the feature lock's commit. `claim` hands each
  repo its worktree + branch. `remove` (archive, never fails) removes only what Maestro created —
  a configured sandbox only once delivery pushed its branches.
- **`project_config.py`** — loads and checks the per-project `maestro.config.yaml` (repo
  build/lint/test commands, QA environment, delivery); `maestroctl preflight` reports missing
  repos, missing `build`/`test` commands (errors) and missing `lint`/`security`/`e2e` (warnings; not
  `e2e` when the repo's `e2e: {status: none}` record says none was found). `apply` writes
  `commands.e2e` only after **`e2e_check.py`** confirms detect-stack's proposal (list mode shows ≥1
  spec, else a cited package.json/Makefile/CI file runs or defines the command; otherwise `none`
  with the reason); `sync` returns `needs_e2e` so /maestro-sync re-checks. Engine
  steps read commands from here, never from skill prose. Spec: `docs/project-config.md`.
- **`repo_checks.py`** — the `verify` script step: runs a repo's configured setup/build/
  typecheck/lint/test in the exact implementation worktree (CI=true, per-command timeout) and
  writes a receipt (commit, command, exit code, duration, log hash per check), plus an engine
  secret scan of the lines the branch added (fails as `secrets`; values never recorded) and a
  scan of the files it added for build or tool output (`__pycache__`, `*.pyc`, `node_modules`, …;
  fails as `build-output`). Its summary names the checks the project never configured. A failing
  check is re-run on the branch's base commit (cached checkout + results under the git-ignored
  `.maestro/baseline/<repo>/`); failing there too makes it `pre-existing`, which does not fail
  verification — but a pre-existing `test` failure makes the release verdict `baseline-failing`
  (`implementation_pool.py`), so autopilot will not release it. With `--reuse-key` (the
  escalation gate's visit count), a fix round that committed nothing reuses the receipt as
  `unchanged`, which the workflow sends to the person instead of another round. The impl loop
  routes on its `passed`, never on an agent's `tests_passed`. Missing config → exit 2.
- **`findings.py`** — review findings decided by the engine: `verdict` reads a reviewer's
  findings JSON (blocking = a blocking finding still `open`/`upheld`); `resolve` reads the author's
  `fixed`/`contested`/`escalated` answers → `proceed` (re-review), `incomplete` (back to the author)
  or `escalate` (a person decides — also when a finding the reviewer upheld is contested again).
  A resolutions file older than the findings file answers an earlier round and is ignored. The HLD
  architecture review, the LLD readiness check and the code reviews in `impl` / `qa-bugfix` route
  on it (the code fixer, `fix-loop`, is the author there). The engine also bounds each loop:
  `verdict --round ${steps.<review>.visits}` sets `limit_reached` after `reviews.max_rounds`
  (maestro.config.yaml, default 3), and `--previous` marks a blocking finding first raised on a
  re-review and not `introduced_by_revision` as `late`; workflows route on `revise` (blocking,
  valid, under the limit), so a limit or a late finding goes to the person, never another round.
- **`review_scope.py`** — before each review, `prepare` writes the diff of the reviewed documents
  since the last round (`<name>.diff`) and keeps one baseline file per review
  (`.engine/reviews/<name>.baseline.json`: each document's text as that round saw it, and the
  ids of the findings it raised, read by `verdict --previous`); a re-review checks the changes,
  not the whole document again. No copies of the documents are kept as files.
- **Design drift** — delivery's `drift_check` (skill `design-drift`) compares every verified
  commit with the approved HLD, contract and LLDs before release; `findings.py verdict` decides
  blocking, which the release autopilot requires to be false.
- **`run_profile.py`** — debug-mode timing (`init --debug`, off by default): every step visit is
  kept under the ledger's `profile.visits` (resolver `_finish_visit`; serving calls stamp
  `served_at_ms`), split into queued, work (agents, scripts) and human (gates, interviews) time,
  plus idle stretches; serving calls rewrite `.engine/profile.md`/`profile.json`, `maestroctl profile`
  prints it. Named `run_profile` so it never shadows the stdlib `profile` module.
- **`brief.py`** — the run brief inlined into every agent prompt by `render_agent_prompt`, at the
  node's `brief:` level (`defaults.brief`, else `minimal`): `minimal` = feature, run mode, this
  step, documents earlier steps produced; `full` adds stages, gate decisions with feedback and
  mid-run notes; `none` = nothing. A step's working files under `.engine/` are not listed as
  documents. Serving calls keep `.engine/run-brief.md` current; `maestroctl brief` prints it.
- **`decision_log.py`** — the feature's one decision log. Each stage's interview record
  (`decisions/<stage>.json`, written by its interview node) is the only store of a decision;
  `sync` renders them into `decisions/decision-log.md` and adds a queue's `settled`
  (evidence-cited) points to its stage's record when no interview ran. With `--slug` the log
  opens with what nobody confirmed (assumptions, items left open, gates answered on autopilot),
  so there is no separate assumption log: each design stage runs it before its review/approval,
  delivery again before the review pack (which shows that section first).
  `validate_prd_questions.py --log <the records' folder> --require-topics --root` refuses a
  question on an already decided topic (any stage) unless it is that decision's single
  `follow_up_of`, and checks every `settled` source exists.
- **`ac_trace.py`** — the acceptance-criteria trace: `design` checks every PRD `AC-xx` is traced
  by a test case (`### TC-…` blocks) and none is unknown; `qa` joins criteria → cases → QA's
  `qa/results.json` into `release/ac-trace.md` with `all_passed`, which the release autopilot requires.
- **`qa_env.py`** — QA's environment and the project's own e2e suites from maestro.config.yaml:
  `plan` (`has_e2e`: some repo has an `e2e` command — QA writes a suite in that framework only
  then, else checks cases directly and adds no framework), `up` (environment.start + ready),
  `e2e` (each repo's `e2e` command in its verified worktree, receipt), `down`; every command gets the code under test as `MAESTRO_WORKTREE_<REPO>` /
  `MAESTRO_COMMIT_<REPO>`.
- **`deliver.py`** — the archive stage's delivery: `delivery.mode` `branch` reports the verified
  branches; `pull-request` re-checks each branch is at its verified commit, pushes it (never
  forced) and opens or reuses a pull request with `gh` — a draft when the release gate's `by` is
  `autopilot`. Writes `delivery.json`.
- **`release_record.py`** — the release record: delivery's `record_release` writes `release.json`
  (who approved, the manifest's sha256) after the release gate approves; the archive's
  `check_release` refuses a feature without it or with a manifest changed since, and returns
  `release_by` for `deliver.py` — so the archive is safe to run later on its own.
- **`infra_scan.py`** — the workspace's infrastructure level (`none` / `containers` / `iac`, from
  Terraform, Helm, Kubernetes, Pulumi, CDK, CloudFormation, Serverless, Ansible, Docker, Compose
  files; overridable in maestro.config.yaml). The HLD stage starts with it: the level decides
  which infrastructure questions are asked at all, and `validate_hld.py --infra-level` requires
  the Infrastructure and operations section for `containers`/`iac`; with `--repos` each change
  must name its owning repository, and those owners (`infra_repos_csv`) are passed to
  `lld_set.py init --require`, which refuses a scope without them.
- **`greenfield.py`** — the new-product path: `check` (no repository discovered), `create` (git
  init + first commit for each repository the HLD's Repositories section lists), `configure` (adds
  the scaffold report's commands to maestro.config.yaml without touching existing entries, runs
  each build and test once, stamps each codebase map in `docs/codebase-maps/`). `workflows/scaffold.yaml` runs
  them around the `repo-scaffold` skill, then records knowledge and pins the commits.
- **`impact.py`** — the feature's impact assessment (`impact.json`, written by the
  `feature-impact` agent right after PRD approval): facts, never a verdict. Schema 3: the
  repositories it changes, `interface_change` (`none`/`lockstep`/`shape`), `data_change`
  (`none`/`additive`/`reshape`), `infrastructure_change`, `compatibility_risk`, and
  `open_decisions` (`{question, kind, evidence}`; the engine owns the kinds — `placement`,
  `integration`, `data-model`, `interface`, `quality` block the light path, `rollout`/`detail` do
  not); it also lists every domain, table, job, queue, endpoint (with its consumers), `INV` rule
  and `CS` scenario it touches, each with a reason and evidence. Schemas 1/2 (booleans + `size`)
  still load, read conservatively. `validate` checks every name is a discovered repository, the
  facts, and that rules/scenarios/domains exist in the living docs (`living_docs.py`); with
  `--prd` it adds every change scenario whose `when_changing` the PRD names
  (`match_scenarios`/`merge`). `load(core_only=True)` — what sizing and the LLD scope
  (`lld_set.py init --choice impact`) use — keeps the repositories and facts when only the item
  lists are wrong. Skipped on greenfield.
- **`impact_trace.py`** — the impact trace: `check --stage hld|lld` requires every impacted item
  to be named in the HLD (a `write_hld`/`revise_from_review` check) or the LLDs (`lld_impact_trace`
  node, `--match` first adds scenarios the LLDs' planned files trigger), or marked "no change needed,
  because …"; gaps go back to the writer. Writes `design/impact-trace.md`, which the HLD and LLD approval
  gates show first. No assessment = valid, and no report is written.
- **`sizing.py`** — after PRD approval, full or light design (light: PRD → LLD → readiness →
  approval; no HLD or contract), decided from a core-valid impact assessment's facts:
  light unless a blocking open decision, an interface or data shape change, infrastructure, "(to
  confirm)" in the PRD, or an HLD from an earlier pass (`--hld`). Repository count never decides.
  Without an assessment the fallback rules: ≤ `design.light_max_criteria` (default 5) acceptance
  criteria, Non-functional requirements None, a one-repository workspace, no "(to confirm)". It
  also prints a plain-words `explanation`, which `design-solution.yaml`'s `how_to_design` gate shows (Go
  with that / Plan the architecture first / Skip the architecture document; autopilot accepts;
  skipped on greenfield or a run-start `path: full|light`); `sizing.py choose` applies the answer
  as the `design_path` step that routes and feeds the LLD stage. Light approvals bind the PRD hash
  instead of an HLD.
- **`prd_source.py`** — when no valid PRD exists, routes the PRD stage: normalize the client's
  own PRD (a 250+ word document, any office/PDF file or a Jira XML export; a client `prd.md` is kept as
  `prd.original.md`) or clarify a short request through the interview.
- **`entry_serve.py`** — a route-only `script` node: its `routes:` branch on values already known
  (inputs or earlier outputs), e.g. workspace sync's "keep current commits; refresh stale docs".
  Does no work, never fails.
- **`workspace_sync.py`** — parallel current-upstream fetch/status, tamper-evident
  fast-forward-only apply, living-doc commit provenance (`docs/provenance.yaml`), and per-feature
  exact-SHA locks. It owns sync safety; the knowledge skill owns only doc-writing judgement.
- **`living_docs.py`** — the deterministic half of the living docs (format v2.3,
  `skills/core/bootstrap/build-knowledge/docs-format.md`): `check` (R1–R9: ID format/placement,
  every cited ID defined in docs, run artifacts and code, every invariant cited in code (warning),
  `repo · path · symbol` anchors and `docs/impact/side-effects.yaml` names resolve, generated
  output current, staleness vs `verified_at`, app calls reach a served route, structure, token
  budgets; `--write` regenerates first), `extract` (inventories from contracts and code —
  OpenAPI, AsyncAPI, SQL, `.env.example`, CronJobs, built-in Go/Python/JS/Dart/Java patterns,
  `docs.extract` from maestro.config.yaml — into `docs/_generated/`, the technical doc's
  connections block, the diagram, `docs/_index/code-to-facts.md` and opt-in facts blocks in folder
  `AGENTS.md`/`CLAUDE.md`), `snapshot`/`stamp` (`verified_at` = HEAD and `status: draft` on docs a
  writer changed), `cited` (the rows behind every ID a PRD/HLD/LLD cites — what LLD, implement
  and review load), `domains` (doc paths for the repos `impact.json` names). **Team-owned
  content** — invariants (`INV`) and change scenarios (`CS`): technical `## Invariants and
  consistency` / `## Change scenarios`, architecture `## Platform-wide invariants`,
  `side-effects.yaml` — is written by people only. The build-knowledge, retrospect and
  workspace-sync writers run `check --write --locked-from <snapshot>` as their handoff check: R9
  fails and the engine restores any change to that content (models propose under `## Proposed
  rules and scenarios`), and a problem inside it is a warning for the team, not the writer's to
  fix. `status`/`rules` (`--repo/--worktree`: the team's rules against a feature's branch; never
  blocks — `impl.yaml`'s `domain_rules` step hands it to the reviewer)/`scaffold`/`next`. Guide:
  `docs/domain-rules.md`. workspace_sync counts a facts-block-only change as managed and pre-v2.3
  docs as stale.
- **`install_workflows.py`** — `install.sh`'s workflow upgrader: per file, add / replace an
  byte-identical stock copy (strict hash, CRLF-normalised, against `.maestro/workflow-manifest.json`
  and `engine/workflow_releases.json`, every version ever shipped) / keep a local edit and write
  `<name>.upstream`. Never writes to an edited workflow. `workflow_releases.json` is generated by
  `scripts/gen_workflow_releases.py` from git history — rerun it after editing `workflows/*`.
- **`stack_skills.py`** — a repository's stack skills: `repos.<repo>.stack` in maestro.config.yaml
  (one name or `go, db`) selects the installed skills tagged `stack:<name>`; the implementation
  pool's `claim`/`bugfix-claim` hand them out by the skill's kind tag: the implement and fix steps
  get everything except `review` checklists (`write_skills_csv`), the reviewer gets the `review`
  checklists and `security` skills (`review_skills_csv`; a stack with no checklist gives it the
  rest). The prompts tell each step to load only the ones covering what the change touches.
- **`install_skills.py`** — `install.sh`'s skill installer: per host, a stock copy (its hash
  matches `.maestro/skill-manifest.json`) is replaced, an edited one is kept with the new files
  written beside it as `*.upstream`, and a copy from before the manifest is replaced with the old
  files kept as `*.previous`. `install.sh --ref <tag|sha>` pins the version, recorded in
  `.maestro/install.json` and reused by a re-run without `--ref`.
- **`ui_server.py`** — the stdlib `http.server` behind `maestro ui`: serves `builder.html`
  and exposes the repo (`/api/workflows` recursively lists every YAML (skipping host,
  vendored and `testdata/` fixture dirs), tagging maestro workflows; `/api/workflow` GET+PUT;
  `/api/runs`; `/api/health`) so the builder is
  folder-aware. Reuses `state.load` + `wf.load_file`; binds 127.0.0.1 only; refuses any Host
  other than 127.0.0.1/localhost/[::1] on its port (DNS rebinding) and any write without the
  per-process `X-Maestro-Token` the served builder page carries (and a foreign Origin);
  path-traversal guarded (`_safe_repo_yaml`); reads any YAML under root except `.git`; writes any `.yaml`
  under root EXCEPT `.git`/`.maestro` (run state stays engine-only) — workflow SOURCE only.

**The action loop** (engine ↔ lead agent): `maestroctl next` prints exactly ONE action as
JSON — `run_agent`, `run_agents` (a parallel wave), `run_lead`, `run_script`,
`ask_interview`, `ask_interview_batch`, `ask_gate`, `ask_input`, `wait`, `done`, or `failed`. Every
serving call first runs engine-owned script steps (`python3 .maestro/engine/*.py`) itself, outside
the ledger lock, and lists them in `auto_scripts`; only other scripts reach the lead. In the
`design` / `auto` run modes (`init --mode`) the same calls record each gate whose `auto:` policy
answers it, and in `auto` each interview whose policy covers it (recommendations become logged
assumptions; listed in `autopilot`); every other gate still goes to the human, which is where
autopilot stops. Served worker
steps are claimed (`dispatched_at` + a `claim` token; `complete --claim` refuses a stale dispatch's
result), and so is an engine script while a serving call runs it (another call never runs it
twice), so later calls return only newly ready work (ready workers before gates) or `wait`, which
lists workers past their node `timeout` as `stale` for `reclaim`; `init` on resume releases claims, `next --peek` re-reads. `run_lead`
is the explicit, bounded exception to worker dispatch; interview actions record one answer or an
atomic batch without dropping unresolved questions. Interview discussions never run in the lead's
context: `interview-brief` renders a read-only brief for an isolated `discussant` subagent (the lead
only relays) or a `/maestro-discuss` side session that records with `--peek` (no worker claim).
Input-bearing gate choices deliberately become a second durable `ask_input` action before
routing. The lead reports back via `complete`, `complete-batch` (a whole wave in one call),
`interview-record`, `interview-record-batch`, `gate-record`,
`gate-input-record`, or `fail`. The LLM never interprets the graph or writes state.

## Running checks

```bash
python3 engine/tests/run_all.py            # the whole engine suite, incl. the no-LLM
                                           # full-SDLC simulation (the correctness proof)
python3 testdata/test_ui_schema_sync.py    # UI <-> engine anti-drift + cross-parser test
python3 engine/maestroctl.py validate workflows/sdlc-main.yaml   # recursive lint
python3 engine/validate_tasks.py testdata/tasks.valid.json
python3 engine/validate_open_questions.py testdata/open-questions.valid.json
```

The evaluation set (`evals/cases/<case>/`: requirement, fixture repositories, expectations,
judge rubric) measures output quality before a release: `engine/eval_setup.py` builds a case's
workspace, a real auto-mode run follows, `engine/eval_score.py score` checks the run's metrics
(design path, questions, validators, verification, AC trace, drift, fix rounds, person gates)
plus a judge's rubric scores, and `summary --baseline evals/baseline.json` flags regressions.
See `docs/evals.md`.

Skill behaviour tests (`evals/skills/<skill>/*.yaml`: a prompt plus expected and forbidden
output) need a model to run but not to check: `python3 engine/skill_tests.py list` prints the
cases; run each in a fresh subagent with its skill, save the reply as `<dir>/<id>.txt`, then
`python3 engine/skill_tests.py check --outputs <dir>`. Run them after editing a skill.

Run one test: `python3 engine/tests/test_resolver.py BackEdgeTest.test_happy_path_no_loop`.
The `invalid-*` fixtures in `testdata/` and `testdata/workflows/` exist to prove the
validators *reject* the hard cases — a validator that accepts one is a regression.
After editing `engine/schemas/workflow.schema.json` or any `workflows/*.yaml`, run
`python3 ui/embed.py` (the sync test fails otherwise). After editing any `workflows/*`, also run
`python3 scripts/gen_workflow_releases.py` (`test_install_workflows` fails otherwise).

## The workflow spec — the invariants that matter

Full spec: `docs/workflow-spec.md`. The load-bearing rules:

- **Minimal authoring defaults**: only `nodes:` is required — `version` defaults to 1,
  `start` to the first node, node `type` to `agent`, omitted routing to `next: end`.
  Keep these defaults working; they are the "simple workflow creation" promise.
- **6 node types**: `agent` (instruction required, optional `execution: lead`, `skill:`
  optional pin — omitted = harness auto-discovery), `interview` (ordered, durable human
  clarification with an engine-written JSON artifact), `gate` (options ARE the edges),
  `script` (stdout JSON becomes routable outputs — the `oq_serve` pattern), `parallel`
  (branches may contain agent/gate/script/subworkflow, never nested parallel),
  `subworkflow` (child steps namespaced `parent/child` in state; depth ≤ 4).
- **Loops are back-edges**, not a construct: any route may target an earlier node.
  Entering a `done` node cascade-resets it plus reachable done steps. Every node has a
  visit cap (`max_visits` → `defaults.max_visits` → 10); exceeding it routes to
  `on_exhausted` (default: a synthesized ask-gate). A route taken through a REAL gate
  option bypasses the cap — the human is the loop bound.
- **Placeholders** are pure text substitution (`${inputs.x}`, `${steps.id.outputs.f}`,
  `${steps.id.branches.k.outputs.f}`, `${steps.id.visits}`; `${config.path}` reads the project's
  maestro.config.yaml — the pack ships none) — no templating engine. `when:` conditions
  support only `==`, `!=`, truthy, `in [a, b]` (`engine/condctl.py`).
- **Artifacts gate completion**: `complete` refuses to mark an agent step done unless
  its `artifact:` files exist non-empty ("proof, not promises").
- **Handoff checks**: an agent's optional `check:` (one `{run}` or a list) runs as engine
  scripts under the agent's step after `complete`; a failure (non-zero exit or `"valid": false`)
  re-serves the same agent with the report, `attempts` times (default 3), then `on_fail`. Its
  JSON fields join the step's outputs and win over the agent's. Writer → validator → repair loops
  are checks; review verdicts and validators where several writers meet stay `script` nodes.
- **Only the engine writes `.maestro/runs/<slug>/state.yaml`** (fcntl-locked, atomic). The
  workflow file's sha256 is recorded; edits mid-run halt until `rebase` or `reset`.

## The YAML subset — engine/wf.py

Zero-dep hand-rolled loader/emitter. Supported: block maps/lists, one-line flow
collections, plain/quoted scalars, `|`/`|-` literals, comments. Rejected by design:
anchors, tags, folded scalars (`>`), multi-doc. The UI's vendored js-yaml must emit
only this subset (`lineWidth: -1` prevents folding); the cross-parser test in
`testdata/test_ui_schema_sync.py` enforces agreement. If you touch `wf.py`, run the
whole suite — the parser underpins everything.

## Conventions when editing

- **Editing a skill = editing its `SKILL.md`.** Keep the frontmatter contract and each
  skill's **Standards**, **Safety** and **`## Output contract`** sections. Skills describe
  only *how* to do the job — they must NOT hardcode artifact paths or pipeline sequencing
  ("runs after X", "in parallel with Y"). The workflow node supplies the artifact path,
  inputs and output fields; the engine renders them into the prompt (`render_agent_prompt`
  in `resolver.py`). A step skill must NOT name Maestro's `.maestro/runs/<slug>/…` layout at all
  (not even as a fallback — that couples a swappable skill to this orchestrator); when a
  standalone `/skill` run has no path from its instructions, tell it to write to "a sensible
  path you choose (and tell the user where)". A step skill also must NOT restate the engine's
  dispatch contract (the "last-line JSON, short scalars" instruction) — `render_agent_prompt`
  injects that into every subagent prompt at runtime; the skill's `## Output contract` states
  only the conceptual output FIELD NAMES. Those field names ARE a machine contract —
  `testdata/test_workflow_skill_contracts.py` checks every workflow node's declared outputs
  appear in its pinned skill. (`skills/maestro` is exempt from all of this — it IS the
  Maestro lead agent, not a swappable step.)
- **A skill is never the source of truth for workflow functionality.** Skills are
  swappable (ours, the user's, a third party's), so any *logic a workflow's guarantees
  depend on* — counting, thresholds, promotion/gating rules, dedup, state transitions,
  anything deterministic and load-bearing — must live in the **engine** (a stdlib module
  invoked as a `script` node, e.g. `engine/mem_consolidate.py` / `engine/oq_serve.py`), NOT
  inside a `SKILL.md`. The skill supplies only *judgement* (what to write), emitting a
  structured artifact the engine consumes; swapping the skill must not be able to change the
  functionality. Litmus test before putting behaviour in a skill: *if someone replaced this
  skill with their own, would a guarantee the workflow relies on break?* If yes, it belongs
  in the engine. (This is why memory consolidation is `engine/mem_consolidate.py`, not the
  retired `consolidate-memory` skill.)
- **`skills/` is the source of truth for skill prose.** `.claude/skills/`, `.cursor/skills/`, `.agents/skills/`
  etc. are installed copies (gitignored, regenerated by `install.sh`) — never edit those.
  The source is organized into category folders (`core/sdlc`, `core/bootstrap`,
  `stacks/<stack>`, plus `maestro`); a new skill goes in the folder matching its role
  (`stacks/<stack>` = its `stack:` tag). Install flattens all of them into the selected host's skills directory,
  so the path is organization only — never reference a skill by folder path, only by `name`.
- **`skills/maestro/SKILL.md` is the orchestrator's contract.** It stays in the lead's context
  for the whole run, so keep it short: cases that apply only sometimes (no slug, one stage, an
  interview discussion, inline mode) live in reference files beside it, read on demand. Its hard rules (never
  edit state, never read artifacts into context, never skip gates, dispatch verbatim)
  are what keep long runs reliable — change them only deliberately.
- **Workflows name skills directly** (`skill: hld-writing`); placeholders are allowed in the
  skill name (`skill: "${inputs.stack}-implement"` replaces the old dispatch glue).
  Model choice: per-node `model:` → workflow `defaults.model` → `haiku`; values pass to
  the harness as-is (haiku/sonnet/opus).
- Nothing in the golden workflow is a stub. The archive stage opens with `check_release`
  (`engine/release_record.py`), then `confirm_archive`, a person-only gate (no `auto:` policy): `skip` ("Not now") ends the stage with nothing pushed and
  `docs/` untouched; the workflow runs standalone later on the slug (input paths default). Its `deliver` step
  (`engine/deliver.py`) reports the verified branches or, with `delivery.mode: pull-request`,
  pushes them and opens pull requests (draft when autopilot approved the release). Build, lint
  and test are engine-run too: `impl.yaml`'s `verify` step runs `engine/repo_checks.py`, which executes the
  project's commands from `maestro.config.yaml` and fails closed when they are missing.
- `.maestro/runs/<slug>/` holds a feature's requirement input **and** all generated
  artifacts + the state ledger. Git-tracked on purpose. Its layout is `engine/run_layout.py`:
  a new run file goes in the folder of its kind (an engine working file under `.engine/`),
  never at the top, and a fact is stored once (render a view from its record; do not write a
  second copy).
- `install.sh` uses `set -uo pipefail` (not `-e`) on purpose — one failed skill
  install must not abort the rest.

## The memory store — `.maestro/memory/`

Repo/umbrella-level, git-tracked, shared across slugs. Three tiers: `incoming/<slug>.json`
(per-run structured drops, race-free), `candidates/<domain>.json` (the engine-owned ledger:
lessons + distinct source slugs, NOT injected), `knowledge/<domain>.md` (engine-RENDERED,
injected via `${memory.knowledge.<domain>}`). A lesson promotes into knowledge only after
**≥3 distinct runs** corroborate it (bootstrap lessons are `authoritative` and render
immediately).

There is a **second knowledge surface**: the committed living docs under `docs/` —
`docs/architecture.md` (repos, Domain map, cross-repo flows, `ARCH-INV` invariants) and per
domain `docs/functional/<domain>.md` (business rules `BR`) + `docs/technical/<domain>.md`
(invariants `INV`, change scenarios `CS`, failure, gotchas). `build-knowledge` authors the
judgement from the codebase; `retrospect` refreshes touched domains after a feature;
`engine/living_docs.py` generates everything the code lists (`docs/_generated/`), checks the
format and IDs, and stamps `verified_at`. Steps load only what they need: the touched domains'
docs, and from LLD on only the rows the design cites. It coexists with the injected lessons store.

**The load-bearing separation (swappable skills):** the consolidation *functionality* —
counting distinct runs, the threshold, promotion, pruning, rendering — is deterministic
engine code in `engine/mem_consolidate.py`, invoked as a **`script` node**. Skills
(`build-knowledge`, `retrospect`) only PRODUCE judgement outputs — the `docs/` knowledge base
and the structured `incoming/*.json` lessons; swapping a skill cannot change how corroboration
works. Reads: the resolver only READS the lessons knowledge tier, once, at `init`, freezing a
per-run `memory-snapshot.json` (`engine/memory.py`). The pre-merge `archive` phase of
`sdlc-main.yaml` runs the harvest by default. Full conventions: `docs/memory.md`.
